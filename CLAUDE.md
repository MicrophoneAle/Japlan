# Japlan

## What Japlan is

Japlan is an iMessage group-chat bot that turns a trip into a points game. Players get a daily board of tasks, claim them in the group chat, and standings are per person.

Spec of record: `docs/PLAN.md`. On any disagreement with code comments, PLAN.md wins. If PLAN is silent, add a TODO and ask; do not invent.

## Architecture

| Layer | Owns |
| --- | --- |
| Linq | Transport only: send, receive, tapbacks, typing, media, groups |
| Next.js on Vercel | Webhook, cron, dispatch. `maxDuration=60` on webhook and daily-board |
| Supabase | Postgres. App uses the **service role**. RLS is off on every public table |
| Gemini | Survey, generation, claim match, vision, conversation tools. Fast vs smart via `GEMINI_FAST_MODEL` / `GEMINI_SMART_MODEL` |
| Foursquare | Places search at trip-create time only |
| Browserbase | Scraping with no clean API. Off the webhook path, except the stateless `search()` primitive from conversation (see below) |

`lib/linq` and `lib/browserbase` are adapters: no game logic. `lib/game` is pure logic: no network calls. Scoring is unit-testable without a phone.

Scoring unit is the individual. Teams are time-bounded, not a score holder. A team task writes the **full** point value to every member, never a split.

## Non-negotiable rules

- **Webhook never blocks.** `/api/linq/webhook` verifies the **raw body**, inserts `events`, returns **200**, then `after()` runs `dispatchLinqEvent`. Linq retries on timeout; awaiting LLM / Browserbase / Foursquare before 200 awards points twice.
- **Idempotency is `payload.event_id` only.** Store it as `events.linq_event_id UNIQUE`. Duplicate insert `23505` is a no-op 200. Never use the `webhook-id` header; it mismatched `event_id` on 19/19 captured deliveries.
- **LLM proposes six axes. `lib/game/scoring.ts` computes points.** Drop any model-supplied `points` / `base_points` on parse. A tool that returns an invented point value is a bug. Conversation must call `get_standings` before stating a score.
- **DM stays in DM.** Budget, diet, allergies, social graph never appear in a group message. Enforce in the prompt and with a test. Group conversation context gets a public survey slice only.
- **Addressed messages always get a reply.** Silence is only for unaddressed traffic (no keyword, not a DM, no task code, no open task context). A valid code that used to die on photo-verification was a bug: photos are a **bonus**, not a gate. Honor and photo resolve on code; only `peer` still needs someone else's tapback.
- **Browserbase never launches a session (`launch()`/Stagehand) on the webhook path.** A live session is seconds-to-minutes and can blow `maxDuration=60`. **Narrow, deliberate exception (2026-09-19):** the conversation tool loop's `search_web` (`lib/handlers/web-search.ts`) calls only the stateless `browserbase.search()` primitive, wrapped in its own 8s timeout, from inside `after()` (already past the 200, never blocks a retry or double-scores). This exists because a chat question like "good teriyaki in osaka" cannot be answered with a real, linkable place any other way; batch research (`lib/itinerary/research.ts`) already used the same primitive off the request path. If `search()` itself proves slow or flaky in practice, cut this rather than widen it to `launch()`. **Second stateless use (2026-10-02):** the *local festival* lookup (`lib/handlers/holidays.ts`) pairs `browserbase.search()` with `browserbase.fetch({format:"markdown"})` to read a city events page, and runs only from the daily cron, which is off the webhook path entirely. Both are stateless API calls, never a session. **Browserbase is not used for public holidays**: those are a closed, published dataset and come from Nager.Date (see below). Browserbase earns its place only on the tier no API carries, a neighbourhood matsuri or a one-off city festival.
- **Foursquare is never called from the webhook path.** Batch at trip creation, or not at all. One narrow exception: the organizer setup resolves the destination answer with one `near` search (`resolveNearArea`, 6s timeout), which is trip creation.
- **No new external APIs.** Gemini, Supabase, Browserbase, Vercel, Foursquare. Three exceptions, all keyless read-only GETs of published open data (the third is Nominatim, `lib/geo/geocode.ts`, added 2026-10-04 for social link placement): weather in `lib/game/weather.ts` (Open-Meteo, predates this rule) and public holidays in `lib/holidays/nager.ts` (**Nager.Date**, added 2026-10-02). Nager was chosen over Calendarific and AbstractAPI because it needs **no key and no account**: nothing to leak, no env var to forget, no free tier to lapse. It is MIT-licensed, covers ~110 countries including every destination `lib/game/city-timezones.ts` can name, and answers `GET https://date.nager.at/api/v3/PublicHolidays/{year}/{cc}` in one unauthenticated call. Country comes from the timezone the destination already resolves to (`lib/game/countries.ts`, IANA zone -> ISO 3166-1 alpha-2). It never throws: a dead host, a 404 for an uncarried country, or an unrecognised shape all read as null and the trip keeps its weekend multipliers.

Validation after generation (code, not prompt): booking, over lowest budget ceiling, diet/allergy/mobility conflict, unsafe/illegal/permanent, duplicate completed, cannot finish before expiry.

## Payload facts (verified against `.captures`)

Do not re-guess these.

- `participant.added` and `chat.created` **never fire** when the bot is added to an iMessage group. Bootstrap is first human `message.received` with `chat.is_group === true` (`lib/handlers/bootstrap.ts`). Ignore `is_me` and outbound.
- Chat id is **both** `data.chat.id` and `data.chat_id`. `chatIdFromData` checks both.
- Sender is `data.sender_handle.handle` (E.164). The object has `is_me`. `is_me` events are ignored. Display name is on the handle object, not the phone string; survey `first_name` can replace it.
- Media is `data.parts[]`, `type=media`, fetchable `url`, `mime` / `mime_type`. **Unverified:** `.captures` holds no media part yet. `[japlan.dispatch] step photo.detect` logs every non-text part's keys; confirm against the first real photo. The declared mime is not trusted (`photoPartsFrom` drops only clear non-images); bytes are sniffed after fetch. iMessage photos are usually HEIC, which prebuilt `sharp` cannot decode: `imageFingerprint` falls back to an exact `sha256:` hash and EXIF is read from the raw bytes.
- Foursquare venue id is **`fsq_place_id`**, not `fsq_id`. Drop results that only have the legacy field.
- **Gemini: `gemini-3.5-flash-lite` rejects `thinkingBudget: 0`** with a bare 400 INVALID_ARGUMENT (verified 2026-09-19). Callers still pass `thinkingBudget: 0`; `thinkingConfigFor` in `lib/llm/gemini.ts` maps it to `thinkingLevel: minimal`, and a rejected thinking config is retried once without it. Never build a thinking config by hand.
- **Gemini tool calls carry a `thoughtSignature`** that must be replayed with the call in the next turn, or the request 400s ("missing a thought_signature"). `completeTurn` reads calls from the raw parts to keep it; the conversation loop echoes calls exactly as made. `gemini-3.5-flash-lite` also ignores `functionCallingConfig: NONE`, so a forced text reply replays tool history as plain text with no tools declared (`flattenToolHistory`).
- Prefer a deterministic parser before a model: dates go through `parseLooseDates` and destinations through `lookupCityTimezone` first; Gemini is only the fallback, and every path is logged `[japlan.setup] step`.
- Task codes: `[A-Za-z]\d{1,2}` as a standalone token (`findTaskCode` in `lib/game/addressing.ts`). Strict: the whole message, or anywhere with the keyword. Loose: a token in a message of 6 words or fewer with no keyword; loose is tentative and stays silent unless it resolves to the sender's own task. Codes repeat per owner (everyone's personal board is A1-A3), unique on `(trip_id, day, participant_id, team_id, code)`; resolve with `findTaskByCodeFor`. Wake keyword: `japlan` (`JAPLAN_WAKE_KEYWORD`), case-insensitive, word boundary.

## Known open problems

These are current, not intended.

- **Second Supabase call in an isolate hangs; the first succeeds.** Suspected client-per-request / PostgREST. `getServiceClient()` is a module singleton, still hangs. Nested embeds (`claims` with `tasks!inner`) were a suspect. Every DB call needs a **timeout**; a hang must not look like silence. `claimAwait` / `dispatchAwait` log `.before` then `.after`; the last `.before` with no `.after` is the hang. `claimAwait` yields once after `.before` so the log can flush.
- **FIXED (2026-10-05), at the client not the call site.** `getServiceClient()` returns a **proxied** client: every `from()` / `rpc()` chain is raced against `DB_TIMEOUT_MS` (8s) and logs `[japlan.db] timeout {label}` naming the table, plus `[japlan.db] slow` over 2s. Timeouts added per call site is how `loadTripLegs` shipped without one and took **every** message down (silent, no error, no `dispatch finished`). Do not add a bare DB call and assume it is bounded somewhere else; it is bounded here, for everyone.
- **Root cause, suspected not yet confirmed:** Next patches global `fetch` for its cache layer and supabase-js uses it. `next.config.ts` `serverExternalPackages` exempts `sharp` and `@browserbasehq/stagehand` but **not** `@supabase/supabase-js`, so every query goes through the patched fetch, and inside `after()` the request context is already torn down. `createClient` now gets an explicit `fetch` with `cache: "no-store"` to take that out of the picture. If hangs survive it, the next suspect is undici connection reuse across a frozen/thawed isolate. The timeout makes either survivable and the log makes the rate measurable.
- **The claim path makes ONE trip query.** Legs come back embedded (`TRIP_COLS_WITH_LEGS`, a PostgREST join in `bootstrap.ts`), so there is no second call to hang. `tripQuery()` falls back to plain `TRIP_COLS` when the embed itself errors (`42P01` / `PGRST200` / a `trip_legs` message), because an unrun 2026-10-03 would otherwise break every trip lookup, which is the outage shape this file keeps warning about. `loadTripLegs` still exists for cron paths and is bounded by the client timeout.
- Use `.maybeSingle()`, never `.single()` (PGRST116 on 0 or 2 rows). Participant uniqueness is `(trip_id, phone)`. Same phone on two trips: always query with `trip_id`.
- **`reaction.added` has never been seen in a capture.** Peer confirmation is implemented and untested against live Linq.
- **Foursquare is out of credits.** Destination profile is hand-seeded: `npx tsx scripts/seed-profile.ts` writes `TOKYO_HAND_PROFILE` from `lib/game/tokyo-profile.ts`. Setup destinations will not resolve until credits return: the raw string is stored and Gemini's timezone (validated) is still used. A destination changed via `japlan setup` stores a `partial` profile; boards generate from it until Foursquare answers.
- **Organizer is a proxy.** Linq never reports who added the bot, so `trips.organizer_participant_id` is whoever sent the first group message (or ran `japlan new trip`). Legacy trips with no organizer: the first participant to run `japlan setup` / `japlan end trip` takes the role.
- **RLS is off** on every public table. Service role only. Do not expose that key.
- **Vercel cron is daily** (`vercel.json` `0 23 * * *`; Hobby blocks more). A board is due when local time is at or after `trips.board_time` (default 08:00) inside `start_date..end_date` (`boardDueNow`), so any tick after board_time posts a missing board. With only the daily tick, most zones get their board late or next tick; `lib/db/migrations/2026-09-22-optional-hourly-board-tick.sql` adds an hourly Supabase pg_cron tick. On-demand boards cover the gap either way.
- **Boards on demand, any day of the trip.** "japlan plans / tomorrow / day 3 / friday / oct 19 / the last day" (`isBoardRequest`, `parseBoardDay`) runs `answerBoardRequest` (`lib/handlers/board-request.ts`): lists the day's open tasks, or builds the board now through `buildBoardForDate`, the one pipeline the cron also uses. Every day is requestable once setup is done; before the trip starts, "plans" means day 1. `boards` (one row per trip-day, inserted before generating: the lock) tracks provisional and delivery; a request that finds the day generating waits for it. `board_requests` is a log (`kind` generate/refill, migration `2026-09-23-board-request-rate-limit.sql`); the only limit is `REFILLS_PER_DAY` (5) refills of the same day per person. Different days are never limited. Future days are provisional and regenerate on their morning unless something on them was claimed. Claimed tasks are never overwritten. A past day with no board stays empty (no retroactive tasks).
- **Generation covers whoever has answered** (`constraintsKnown`): someone mid-survey does not hold up anyone else's board. They get "finish your survey" for their own request, then a top-up on that day once done (`deliverExistingBoard`, late-joiner path in `answerBoardRequest`).
- **Stop refusing.** A decline is kept only when doing the thing would be wrong (someone else's task, double award, a day outside the trip, unknown allergies for the asker's own tasks, unsafe freeform). Removed on purpose, do not reintroduce: the conversation hourly cap, freeform once-per-day, one-generation-per-day, "trip hasn't started", "board being made, try later", "claim in the group" for DM claims (DM claims confirm in group and DM), "you're not on this trip" (someone new in the group chat is added and surveyed, `joinLateParticipant`). Day letters cycle past Z (`dayLetter`); `findTaskByCodeFor` prefers the latest day. Trips up to 90 days (longer is treated as a typo). Failures say "that's on me", not a refusal.
- **Foursquare PAYG storage:** do not cache names/hours in `places` indefinitely. Only `fsq_place_id`, photo ids, and address ids may be stored long-term. Current `places` rows still store names; do not add more cache of licensed fields.

## Conventions

- All user-facing strings live in `lib/game/copy.ts`, never inline. Conversation system prompt: `CONVERSATION_SYSTEM_PROMPT`. Help: `HELP_TEXT`.
- **House style, deterministic copy (`lib/game/copy.ts` template strings: confirmations, boards, errors, settings): lowercase, always** (no exceptions for emphasis; use emoji or letter elongation instead, never caps). Contractions always. Letter elongation for emphasis (heyyyy, noooo). Exclamation marks are fine, used for real excitement, not on every line. These strings are short, transactional receipts, exact-matched by a wide swath of tests (`claims.test.ts`, `plan-changes.test.ts`, `board-schedule.test.ts` and others assert their literal wording): changing one means updating its test in the same change, deliberately, not as a side effect of a voice pass. Three emoji are functional regardless of any voice change, never swapped for a different one: `✅` marks a claim confirmed, `📸` marks a photo bonus, `👍` is the literal iMessage tapback `handlePeerReaction` checks for when telling someone how to peer-confirm a claim (see reactions, below). One message, never two.
- **House style, free-form conversation (`CONVERSATION_SYSTEM_PROMPT` in `lib/game/copy.ts`, everything `lib/handlers/conversation.ts` sends): a witty, socially-aware friend, not a default-Gen-Z chatbot (revised 2026-09-19, replacing an earlier "slang is the default register, reach for emoji freely" draft that read as performing a demographic rather than talking like a person).** Lowercase always, contractions always, same as the deterministic copy. Slang (fr, ngl, no cap, lowkey, bet, say less) is seasoning: plenty of good replies use none at all, never more than one per message, never the same one twice in a row. A handful of tics (bro, nahhh, lmao, fr fr, 💀, "that's crazy", "you're cooked", "honestly...", "absolute cinema") are not a default reflex; each is fine on the rare message where it's genuinely the funniest option. Emoji are occasional seasoning, not punctuation: most replies want zero. Vary sentence length, opener, and joke shape on purpose, checking the model's own last couple of lines in the chat history so two replies in a row never read like the same template. Answer real questions directly and take a side on real choices instead of listing options; use context (survey answers, recent chat, tool results) without narrating the mechanism; humor comes from callbacks to what actually happened, not a bit performed from nowhere; follow-up questions are earned, not a reflex closer. See the prompt itself for the full spec; `lib/game/settings.test.ts` and `lib/game/conversation.test.ts` pin a few load-bearing substrings (the "you do not enforce rules" language, "never a point value", no literal `<number> point(s)`), so a future rewrite should grep those tests before publishing a new draft.
- **No em dashes** anywhere: code, comments, copy, this file.
- **Outbound reactions** (`lib/linq/send.ts` `react(messageId, tapback | { emoji })`, wraps `client.messages.addReaction`): a tapback, not a text message, so it never counts as the reply and never blocks one. Two call sites: `lib/handlers/claims.ts`'s `reactToClaim` fires a 🔥 custom-emoji tapback on the claiming message whenever `applyAwards` actually pays out (skipped when the daily cap zeroes it), from `resolveKnownTask`'s `sourceMessageId` (the inbound message's `data.id`, threaded through from `handleGroupClaimInner`). The conversation tool loop also exposes `react_to_message` (`lib/handlers/conversation.ts`), letting the model tapback something funny or hype instead of, or alongside, texting back; it reacts to the current turn's inbound message (`miss.data.id`). Both call sites swallow a failed reaction (logged, never thrown): a tapback is flavor, never load-bearing, and must not touch the claim, the score, or a text reply already sent. Do not use this for peer confirmation, which stays inbound-only (a human tapping `👍`/`❤️` on a message Japlan sent, read by `handlePeerReaction`).
- **iMessage effects** (`lib/linq/send.ts`, `MessageEffect`, `sendText`'s `opts.effect`): screen effects (`confetti`, `fireworks`, `lasers`, `sparkles`, `celebration`, `hearts`, `love`, `balloons`, `happy_birthday`, `echo`, `spotlight`) animate the whole screen; bubble effects (`slam`, `loud`, `gentle`, `invisible`) animate only the message bubble. Two different things in iMessage; Linq exposes both under the same `MessageContent.effect` field. Used sparingly on purpose, exactly two places: `confetti` once, on the final standings message when a trip ends (`lib/handlers/trip-lifecycle.ts`; "once" falls out for free, since that send only runs the one time `end_trip_confirm`'s guarded update actually flips the trip to `complete`); `fireworks` on a claim confirmation whose task clears `CLAIM_EFFECT_POINTS_THRESHOLD` (20, `lib/game/scoring.ts`'s `claimEarnsScreenEffect`, checked against `rawTaskPoints` — `computePoints` on the task's own `axes_json`, never the stored `base_points`, which is already scaled by `dayValueMultiplier` and would fire on almost everything by the final day). Never on a capped claim (nothing was actually awarded), boards, standings, or conversation. An effect rides in the same send as the text, so it cannot fail independently: `sendText` retries once, plain, if the effect-carrying send throws, so a decoration never costs the confirmation. If `claimEarnsScreenEffect` fires too often in practice, raise `CLAIM_EFFECT_POINTS_THRESHOLD` rather than removing the feature.
- **Contact card** (iMessage Name and Photo Sharing, Linq's `contactCard`/`chats.shareContactCard`): a one-time account-level setup, `scripts/setup-contact-card.ts` (run manually, `npx tsx scripts/setup-contact-card.ts`), registers "Japlan" + `public/assets/japlan-contact-card.png` for `LINQ_FROM_NUMBER` (uploads the logo through Linq's own attachments API first, so this never depends on the app being deployed anywhere; `create()` 409s if a card is already active, so the script falls back to `update()`). Separately, `shareContactCardSafely(chatId)` (`lib/linq/send.ts`) pushes that registered card into a specific chat — needed because registering the card once does not make it show up everywhere; Linq's own docs say to share it into each chat after that chat's first outbound message. Wired into every "first message to a new chat" site: the group intro (`lib/handlers/bootstrap.ts`, gated by the same `intro_sent_at` claim so it only fires once per trip), each participant's first setup/survey DM (also in `bootstrap.ts`), and solo bootstrap's first DM (`lib/handlers/solo.ts`). Fire-and-forget like `react()`: a failed share never blocks or fails the message it rides after.
- **Web search** (`lib/handlers/web-search.ts` `searchTheWeb`, conversation tool `search_web` in `lib/handlers/conversation.ts`): real, linkable results for a restaurant, ticket, or booking-site question, backed by `browserbase.search()` (see the Browserbase exception above), never `launch()`/a live session. Missing `BROWSERBASE_API_KEY`, a timeout (8s), an error, or zero `https://` results all come back as a typed `{ok:false, reason}` and never throw; the model falls back to its own best guess per `CONVERSATION_SYSTEM_PROMPT`. The tool result's `{title, url}` pairs flow into `toolText` like any other tool, so `checkReply` accepts a named place or number that came from a search result the same way it accepts one from `get_open_tasks`.
- Claim/dispatch steps log `[japlan.claim] step` / `[japlan.dispatch] step` with `.before` / `.after`. Hang = last `.before` without `.after`.
- Photos: `photo_bonus_max` is a ceiling, not a requirement. Bare code awards `base_points`. A matching photo within `JAPLAN_PHOTO_BONUS_WINDOW_MS` (default 2h) adds bonus onto the existing claim (`claims.photo_claimed_at` blocks a second bonus). Daily cap 120 still applies to the bonus.
- Vision (`scorePhotoFidelity`): two easy questions, evidence not proof. First "does this plausibly relate" (`PHOTO_RELATES_SYSTEM`, biased to yes, returns `seen` too), then a 1..max score only on yes, so a yes always pays. The old "does this photo show the task" rejected benches for bench tasks. An empty or unreadable model answer is a failed check ("couldn't check that photo"), never "doesn't look like". The image is auto-rotated and downscaled first (`prepareForVision`; HEIC goes as-is). Every check logs `[japlan.claim] step gemini.vision.raw` with what the model saw and its raw JSON. Recalibrate against `npx tsx scripts/vision-fixtures.ts --runs 3` (live Gemini; 2026-09-19: 53/54, 0 false no); `--extra` takes private photos by local path, never commit them.
- EXIF window: a photo counts if taken between the earlier of trip start and the day the task was made, and trip end. Camera-roll shots older than the task are still refused.
- Board lines carry tier from the points: `A1 · title · medium (13)`. Future days read `Day 2, subject to change`.
- **Social link resolution** (`lib/game/urls.ts` pure, `lib/social/read-link.ts` adapter, `lib/handlers/social-links.ts`, table `social_links`, migration `2026-10-04`): a link dropped in the chat becomes a place on the itinerary. Feeds the existing suggestions path (`places` with `source='social'` + `suggested_by`), so it anchors on a day and shows as `+ <place> (Dev's pick)`.
  - **NO SESSIONS. Nothing on this path calls `browserbase.launch()` or Stagehand**, so there is no session to leak, no concurrency limit to exhaust and nothing to close in a `finally`. Every read is stateless. A test (`social-links.test.ts`) fails loudly if anything ever reaches for `launch()`.
  - **Measured against the live sites 2026-10-04, before building.** `tiktok` -> the **keyless oEmbed endpoint** (`~200ms`, full caption including venue); `browserbase.fetch` on TikTok is **blocked**, 2/2 returned its bot page at 122 chars, so it is deterministic and must never be retried through a browser. `instagram` -> `browserbase.fetch` (`~1.5s`, ~23k chars): the logged-out page keeps the caption, hashtags and often a **street address** under the "Log In" chrome, while a crawler-UA fetch gets **no `og:` tags at all**. 1 of 4 IG URLs returned 0 chars, so a miss is a real fraction of traffic. `maps` -> parsed straight off the URL, one redirect hop for a short link, **never a browser**. `article` -> `browserbase.fetch`.
  - **Two halves, deliberately split.** `captureLinks` runs on the **webhook path** and is one INSERT per link: no fetch, no model, no Foursquare. `resolveQueuedLinks` runs on the **cron**, off the request path entirely.
  - **Silence rule:** a link that resolves to nothing produces **no message at all**; only a hit speaks, in one line (`socialPlaceAddedLine`). "Couldn't read that tiktok" on every link is worse than saying nothing.
  - **Unresolved is a first-class outcome, not an error branch.** A caption we read but that names no venue is stored `status='unresolved'` **with the caption kept**, so the group can clarify later. Do not turn this into a discard.
  - **`fsq_place_id` stays null** while Foursquare has no credits: a name plus the address off the caption is enough to put a place on a day. `places.resolved_at` + the partial index `places_needs_fsq_idx` are exactly the backfill query for when credits return. A missing id never fails the resolution.
  - **Rate limit:** `RESOLUTIONS_PER_TRIP_PER_HOUR` (20, generous on purpose: the failure case is ten links at once, not one link being slow). `MAX_ATTEMPTS` is 1, and the attempt is counted **before** the try so a crash cannot make a link retry forever. Neither Instagram nor TikTok becomes readable on a retry.
  - **Coordinates, or an honest no.** IG and TikTok give a name and often a street address but never a lat/lng, and `fitSuggestion` needs coordinates. The cascade lives in **`locate()` (`plan-changes.ts`), shared by every path that places a venue**: the conversation tool, survey must-haves and link resolution. A place the trip already knows / `resolvePlace` against the profile, then **Nominatim on the VENUE NAME plus its city** (`lib/geo/geocode.ts`), then the named neighbourhood, then nothing. It was once wired into link resolution only, which is how a reel naming Shibuya Sky came back "couldn't pin it on a map": the conversation tool answered first and had no geocoder. The profile is a hand-seeded list and will never hold every venue, so any path that can name a place needs this. **Geocode the name, never the address**: measured 2026-10-04, Nominatim reads `"Ramen Break Beats, Tokyo"` (exact shop) and **cannot** read `"〒153-0063 Tokyo, Meguro City, 4 Chome−21−19"`. The address is still stored on the place, it is just not the lookup key.
  - **Venue precision or nothing.** A result with `place_rank < 20` (a city, a prefecture) or more than 150 km from the trip centre is **rejected**, not used. Placing a suggestion at the city centre is a guess dressed as an answer, and a wrong day is worse than an honest "not yet". With no coordinates the fit is `no_location`: the place goes on the ideas list, nothing is anchored, and the line says `not sure which day yet`.
  - Nominatim is keyless open data, the same class of source as Nager.Date and Open-Meteo. Its usage policy (1 req/sec, identifying User-Agent) is honoured in `geocode.ts`; volume is bounded by the hourly cap above.
  - **Name cleaning is deliberately absent.** Measured: Nominatim returns Shibuya Sky at `place_rank=30` for `"Shibuya Sky, Tokyo"`, `"渋谷スカイ, Tokyo"`, `"📍渋谷スカイ #tokyo"` and `"Shibuya Sky 🌇 #tokyo"` alike. Stripping emoji, hashtags and pins buys nothing; do not add it back because it looks prudent.
  - **Pacing short-circuits rather than queueing.** `geocodePlace` reserves its slot **synchronously** (`reserveSlot`), because checking a last-call timestamp and then awaiting lets two callers through at once. If the slot is more than `MAX_PACING_WAIT_MS` (1s) out it returns null immediately: this is on a user-facing path now, and a suggestion with no coordinates beats a reply that took three seconds. Per-isolate; the per-trip hourly cap bounds real volume.
  - **One venue, one row, one message.** `existingSuggestion` (`lib/game/suggestions.ts`) matches on a normalised name across `SUGGESTED_SOURCES` (`suggestion` + `social`), used by both `saveSuggestion` and the link resolver. A pasted link is handled twice by design (the conversation tool answers live, the cron resolves the queued row), so whichever lands first owns the row; the second attaches, fills in coordinates or an address the first could not find, and **says nothing**.
  - **Maps links need neither model nor geocoder**: the URL carries the name and the coordinates, so that path is pure string work and is the most reliable one in the feature. It is checked first in `readLink`.
  - Both paths land through `anchorSuggestion` (`plan-changes.ts`), the same fit-and-anchor the typed-in `add_suggestion` tool uses, so a place from a TikTok behaves exactly like one someone typed.
  - **Every attempt is logged** with kind, status, outcome and the extracted text, so the real hit rate comes from live traffic: `select kind, status, count(*) from social_links group by 1, 2`.
- **One show suggestion per trip** (`lib/handlers/show-suggestion.ts`, table `trip_events`, migrations `2026-10-05` + `2026-10-06`): if somebody's `must_have` names something ticketed (`TICKETED_RE`), the best matching row in `trip_events` becomes ONE group message, attributed by name, with the URL last and alone on its line so iMessage renders the preview card. `trips.show_suggested_at` is the once-ever guard, claimed BEFORE sending via `update ... where show_suggested_at is null` so two cron ticks cannot both send.
  - **Inventory comes from `trip_events`, never from an API at match time.** A row is a row: `source='seed'` (hand-assembled, `scripts/seed-events.ts`) and `source='discovery'` go through identical matching, attribution and copy, so a seeded demo exercises the real path rather than a mock of it.
  - **Ticketmaster is kept for non-Japan trips and must not be retried for Japan.** Probed 2026-10-04 with a live key: `countryCode=JP` returns 216 events for a year, all one sporting-competition feed, with **0% venue lat/lng, 0% priceRanges and 0% purchase URL**, classifications literally `"Undefined"`. `city=Tokyo` returns 0; `classificationName=Music` in JP returns 0. The detail endpoint returns identical keys, so a second call recovers nothing. A London control had 100% url / lat/lng / classifications, which is how we know those 0%s are real absence and not a parsing bug.
  - **No budget check on events, deliberately.** `priceRanges` was **0% filled in London music, New York music and US-wide** too, so a budget rule suppresses every suggestion in every market rather than filtering any. `trip_events.price_note` is a NOTE, not a number: it says what is known, and the copy says the price is unknown when it is.
  - **A time is never invented from a date.** `eventWhen` formats "saturday 7pm" only from a real stored timestamp, because the message says the hour out loud. `seed-events.ts` refuses to write any row whose url still contains `example.com`: a fabricated ticket link is worse than no feature.

- **`must_have` is group-shareable; everything else in the survey is not.** `PUBLIC_SURVEY_IDS` (`lib/game/conversation.ts`) is an allowlist and now has a test (`conversation-privacy.test.ts`) that had never existed: it asserts `must_have` is shared, that 16 sensitive fields are not, that no private **value** appears anywhere in a serialised group slice, that DMs still get everything, and that the list is fail-closed so a new survey field is private until someone puts it on the list on purpose. Survey v2's ids moved to `PRIVATE_SURVEY_IDS` (2026-10-05): they were on neither list, so they reached no prompt at all, including the person's own DM.
- **Per-leg destinations** (`lib/game/legs.ts` pure, `lib/handlers/legs.ts` I/O, table `trip_legs`, migration `2026-10-03`): a trip is a list of legs, a city and the dates you are in it. Legs **partition** the trip's dates (no gaps, no overlaps), so every date belongs to exactly one. Nothing reads `trips.destination` / `trips.timezone` directly any more.
  - **Resolvers:** `zoneFor(trip, date)` / `cityFor(trip, date)` for a known date, `zoneNow(trip, now)` / `todayFor(trip, now)` for right now, `isTravelDate`, `legsLabel`, `legCities`. Legs ride on the trip (`trip.legs`, attached by `asTripWithLegs` in `bootstrap.ts`), so every call site stays synchronous and costs no query of its own. That matters on the claim path, where a second round trip is the known hang.
  - **Single-city trips are identical by construction.** `legsOf` synthesises one leg from `trips.destination / timezone / dates / destination_profile_json` when none are loaded, which is exactly what the old code read. A missed migration therefore degrades to today's behaviour rather than breaking every call site. `lib/game/legs.test.ts` pins this.
  - **`legForNow` does NOT iterate.** Re-reading the date in the guessed leg's zone oscillates: when the next city is behind the current one there is a window (Tokyo is already the 5th, Bangkok still the 4th) where each leg's zone points at the other. It instead takes the **last leg that has started in its own timezone**, which is monotonic in time, so it is stable and never flips back. In that window it keeps them in the city they have not left yet. Do not "simplify" this into a re-read loop.
  - **Profiles are per leg and lazy** (`assembleDestinationProfile({trip, people, date})`): two Foursquare searches when that leg is first needed, not every leg at trip creation. A single-leg trip falls back to `trips.destination_profile_json` (where every profile lived before legs, and where `scripts/seed-profile.ts` still writes); a multi-leg trip never falls back, or Tokyo's profile would serve Osaka.
  - **`places.leg_id`** keeps clustering inside one city. `existingChatPlaces` filters by leg; a row with no leg still counts, which on a one-leg trip is every row.
  - **Travel days:** the first date of a leg that follows another one (the **arriving** leg owns it). The window starts at `TRAVEL_DAY_START_MINUTE` (16:00) instead of `board_time`, the default count drops to `TRAVEL_DAY_MAX_TASKS` (3, an explicit "7 attractions" still wins), and `travelDayGuidance` tells the model they arrive late with bags: the first meal, a walk around the block, nothing ticketed or far. Header reads `Day 5 · Osaka · travel day`.
  - **Setup stays light.** "Tokyo" is one leg and takes exactly the path it always did. `splitDestinationAnswer` splits on `and / then / -> / via / , / ;` but folds a trailing country back on, so `tokyo, japan` is one place and `tokyo, osaka` is two; word boundaries keep `Auckland`, `Thailand` and `Andorra` intact. Only the FIRST city is resolved in full (places lookup plus Gemini timezone); the rest use the offline city table, so a multi-city answer still costs one Foursquare call, not one per city. Legs are written by `syncTripLegs` once destination and dates are both settled, and the destination string round-trips.
  - **Multipliers are per leg**: a Tokyo to Seoul trip has two countries, so `nationalHolidays` loops legs and clips each country's holidays to that leg's own dates. `multiplier_days.leg_id` records which. `unique (trip_id, local_date)` still holds because legs partition the dates.
  - **Wrapped:** `trip.destination` is now `legsLabel` (`Tokyo → Osaka`), and a `cities` stat appears only when there is more than one (it would read "1 cities" otherwise). `distance_km` is still 0 (claims store no location); legs now make it computable. There is no route map and never was.
- **Day multipliers** (`lib/game/multipliers.ts`, `lib/handlers/holidays.ts`, migration `2026-10-02`): some days are worth more, for **everyone on the trip**, so people go out on the days the city is alive. National holiday **3x**, major festival period **2x** (golden week, obon, carnival, songkran), weekend **1.25x** (friday, saturday, sunday). Best one wins, never a sum: a holiday on a saturday is 3x, not 3.75x.
  - **A special day REPLACES `dayValueMultiplier`, never compounds with it.** `scoring.ts` scales base_points by which day of the trip it is (final day doubles). The higher of the two applies and the other is discarded (`combinedMultiplier` = `min(3, max(dayValue, event))`), so a holiday on the final day is 3x and not 6x: tier bands hold and one claim cannot empty the cap. Concretely, `persistableTask` writes **unscaled** `base_points` whenever it writes a multiplier, so `⚡ golden week, everything's 2x` is literally true of the numbers printed underneath it.
  - Two consequences, both deliberate. A **weekend stops mattering from day 3 onward** (`dayValue` 1.3 already beats 1.25) and the board correctly says nothing; holidays and festivals always still pay. And **friday is a whole 1.25x day, not friday evening**: an evening-only window cannot be baked into a task's points, and 1.25x only ever beats `dayValue` on days 1-2 anyway. Both live in `taskMultiplierFor`, the one place the two scalings meet.
  - The alternative (announce the factor left over after `dayValue`, keep base_points scaled) is equally correct and unreadable: real Golden Week 2026 data comes out as `everything's 2.61x`. Do not reintroduce it.
  - **Stored on the task at generation** (`tasks.day_multiplier` / `multiplier_reason`, written by `persistableTask`). A claim reads the task, so it pays what the board promised even if the local day rolled over mid-claim, and the claim path does **no** extra DB call. Old rows and ordinary days have null and pay `base_points`.
  - **The cap scales, it is not raised by a flat amount** (`capForMultiplier`: `cap * multiplier`). The cap bounds how many tasks one person can farm in a day, not what a day is worth, so scaling keeps the number of claims needed to hit the ceiling constant. A flat raise would mean something different at every multiplier, and an unscaled cap would swallow the whole bonus for exactly the people who clear their board.
  - **Where it surfaces:** the board header, last, after route and weather (`Day 3 · Asakusa → Ueno · 18°C · ⚡ golden week, everything's 2x`, `multiplierHeaderPart`); **one** group message in the morning (`multiplierDayAnnouncement`, from `deliverMorningBoards`, skipped on solo), never one per claim. Claim confirmations stay one line and just say why the number is bigger (`🔥 3x sports day`).
  - **Generation notices too** (`specialDayGuidance` in `generate.ts`): lean the board toward what is actually happening, and on a **national holiday** warn that museums, shops and ticketed sites are shut and transit is packed. A 3x board full of closed venues is worse than an ordinary day.
  - **Where the data comes from:** holidays from Nager.Date at setup (`refreshTripMultipliers(trip, {festivals: false})` in `lib/handlers/setup.ts`, trip creation, keyless, 6s cap); local festivals from Browserbase on the daily cron only. Both tiers store independently (`storeSource`), so a failed scrape never deletes found holidays and vice versa. Everything looked up passes `validSpecialDays` first: the date must parse and sit inside the trip, and the **source** decides the multiplier, so no page can name its own number. Weekends need nothing stored and work with no key, no migration and no country. A miss is normal, never an error. Re-looked-up weekly (`REFRESH_AFTER_MS`); a destination change clears `multipliers_checked_at`.
- Weights (2026-09-19): boldness 1.6, scarcity 1.5, cultural 1.4, time 0.9, physical 0.8, aesthetics 0.6. Points 7 (all 1s) to 34 (all 5s); light 7-15, medium 16-24, challenging 25-34.
- Generation is template-first: the model names a `template` from `boardTemplates()` for every task (unknown template = rejected), except one `curveball` on roughly one board in four (`isCurveballBoard`, seeded per trip/day/assignee; stored `source='curveball'`). Code clamps the model's non-time axes into the template's ranges. Prompt: weak-task definition, "go look at X" is the weakest archetype, at least one stranger task, boldness by count (`boldTasksWanted`), every title already on the trip.
- Duration (`lib/game/duration.ts`): minutes = venue time (hand table by Foursquare category, restaurants by price) + travel (haversine x1.3 at 15 km/h city, 4.5 km/h walking) + friction (boldness 1-5: 0/5/20/30/40). Bands: sidequest <20, light 20-45, medium 45-120, challenging 120+ (time axis 1/2/3/4-5). Code overrides the model's time axis when more than one band apart. Sidequest templates (`duration: "sidequest"`) and sidequest-length tasks never go on the board. The sidequest delivery system (PLAN step 7) is not built yet.
- Day planning (`lib/game/day-plan.ts`, `lib/game/plan-board.ts`): usable window from `board_time` (plus pace late start) to a pace end (relaxed 20:00, steady 21:00, chaotic 22:00) minus prorated meals; for today it starts now (at least a 2 h evening). Main tasks fill 60-70% of usable minutes (max 6), topped up from templates when short or with no stranger task. No two tasks share a place or template (`boardConflict`), kinds stay varied. Ordered by nearest-neighbour route, labelled morning/afternoon/evening; `tasks.slot` and `tasks.duration_minutes` persist them (migration `2026-09-24-task-day-planning.sql`). Board: `Day 3 · Asakusa → Ueno` then `morning    A1 · title · medium (18)`.
- **Survey answers are filters or weights, enforced in code** (`lib/game/preferences.ts`, `validateGeneratedTask`, `selectForDay`). Filters: sociability (`love_it` at least 1 stranger task, `small_doses` exactly 1, `rather_not` none, by the template `needs_stranger` flag plus a fail-closed title check; unanswered counts as small doses), diet by what it is (`dietary_detail`, `lib/game/diet.ts`: dishes that carry it and blind food are out, other food stays; an unreadable restriction still means no food), budget with the template's `typical_cost`, mobility (title plus template physical 3+), drinking/under-18 (alcohol), cautious eater (blind food), blackouts (shrink the window), under-18 (no tasks, PLAN's 18+ gate). A group takes the most restrictive answer. Weights: interest picks (`interest_picks`, top two of seven), boldness target from difficulty and chaos (chill 2.5, still at least one boldness-3 task), suggested places, avoided categories. Every board logs `[japlan.generate] personalization` with which fields reached the prompt and which acted as filters. `npx tsx scripts/survey-diff.ts` prints two opposed survey vectors' live boards side by side.
- **One group until someone says otherwise** (`lib/game/split.ts`, `lib/handlers/plan-changes.ts`). No split: one plan for everyone, cloned to each person (same schedule and codes, claimed individually). The conversation tool `record_split` turns "me and jess are doing shimokita", "i'm sleeping in", "splitting after lunch" into time-bounded teams for that trip day (`teams.day/starts_at/rejoin_at/rejoin_place/area`); code places "me", names and "everyone else", honours a couple's "together" privately, and asks only about people it could not place. Different starts without a stated meeting converge 3 h after the late start. The rest of that day is re-planned per group (`replanDay`; claimed tasks stand): each team its own window ending near the rejoin place, everyone together after. `record_regroup` dissolves the day's teams and re-plans together.
- **The group's own suggestions** (`add_suggestion`, `avoid_category`, plus survey `attractions`/`paid_attractions`): a `places` row with `source='suggestion'` and `suggested_by`, resolved against trip places and the profile (never a live Foursquare call). It anchors (an `itinerary` row) on the earliest day whose stops are within 2.5 km, else the first unplanned day, else stays on the ideas list with the day it would suit. Anchors ride the day's route and show on the board as `+ teamLab (Dev's pick)`; generation prefers tasks at suggested places. "we don't want to do temples" sets `trips.category_weights.temples = 0.3`, the same factor a thumbs-down rating (score 1-2) applies. Migration `2026-09-25-splits-and-suggestions.sql`.
- **Survey v2** (`lib/game/survey.ts`, `SURVEY_V2` in `survey-questions.ts`): intro, then at most 8 things: four either-ors (`ab_food_outdoors`, `ab_discover_iconic`, `ab_culture_nightlife`, `ab_pace`), `budget_band`, `hard_constraints`, `must_have`, `splitting` (groups only). Follow-ups only when they change a decision: `fu_budget` (unusable budget, once, then the middle band at low confidence), `fu_constraints` ("a few things"), `fu_allergy_cc`, `fu_diet_strict`, `fu_split`. Vague answers are stored low-confidence, never re-asked. Anything is accepted: an answer to a later question is stored `early` and that question skipped; "wait, go back" / "change my last answer" goes back; a reply the parser cannot read goes to `interpretSurveyReply` (answer, or an in-voice aside, checked by `checkReply`, then the question re-asked another way). Old keys (`pace`, `budget`, `dietary*`, `mobility`, `sociability`, `chaos`, `interest_picks`, `social_*`) are still written by `compatAnswers` (`lib/game/prefs.ts`), so every filter reads the same fields. Old mid-survey rows restart at the first v2 question.
- **Sidequest onboarding** at trip start (`startSidequestOnboarding`): level 1-4, red lines only for 2 or 3. Red lines are hard filters (`red_line` in `validate.ts`; "strangers" sets `sociability=rather_not`). Replaces the chaos and sociability questions. Hard no's in their own words ("no heights") are `hard_no`. A diet said as a preference is a soft weight (`softDiet` in `plan-board.ts`), not a filter; allergies always filter.
- **Contextual questions are not built.** Drinking, food adventurousness and blackout times left onboarding, but nothing asks them in context yet; their old answers still work, and `update_my_setting` can set them.
- **Weights and profiles** (`lib/game/prefs.ts`, `lib/game/profile.ts`, `lib/handlers/profiles.ts`): `participants.prefs_json` holds per-dimension weights with confidence (either-or medium, vague/skipped low, stated high). Behaviour nudges them (`learnFrom`: claimed task, suggested place, avoided category); a stated preference ("i'm not that into food") sets them (`statePreference` via `update_my_setting`). `participants.profile_md` is a few sentences of prose, hard constraints verbatim (`constraintLine`), rewritten only when a weight moves 0.1 or more since the last write. `trips.group_profile_md` is agree/split, pace, the union of hard constraints with no names, and must-haves. **DM-private:** a shared board's prompt gets only the group profile; a one-person board gets that person's own; "japlan what do you know about me" (the `profile` command only; there is no conversation tool for it) answers in DM, rebuilt fresh in the second person from current answers (`profileFor`), and in a group says "that's in your dm." `profile_md` (third person) is what generation prompts read. Tested in `lib/handlers/survey-engagement.test.ts`.
- **Group engagement** (`lib/game/engagement.ts`, `lib/handlers/engagement.ts`, state in `trips.engagement_json`): the keyword engages. Engaged, the bot follows without the keyword while `judgeStillEngaged` says so (no answer = leave). It leaves by rule on a 20 min gap, 4 messages in a row from people, or no bot line in the transcript. Unaddressed messages are judged by `judgeShouldJoin` only when `entrySignal` finds a game topic (score, plan, claim, split, suggestion, known place). A bare group photo with no signal is checked against open tasks (a vision call per photo) and a miss is silence. "japlan chill" / "shut up japlan" / "stop japlan" / "we're good japlan" reply `STOP_LINE` and only a direct mention brings it back. Every decision logs `[japlan.engage] decision` with reason and `via`. DMs are unchanged.
- **Transcript** (`lib/chat/transcript.ts`, table `chat_messages`): every inbound message (dispatch) and outbound message (`lib/linq/send.ts`) per chat. The conversation reads the last 15 lines of its own chat and logs `[japlan.conversation] context {lines}`. The open task list is no longer in the prompt: facts come from tools.
- **Reply vetting** (`lib/game/reply-check.ts`, then `judgeRelevance`): before a model reply is sent, an unknown task code, a number no tool returned this turn (and the person did not say), an unknown person claim, an unknown named place, or empty/malformed text is discarded; so is a reply the relevance judge says does not respond. The discard sends `DISCARD_FALLBACK` and logs `[japlan.conversation] discard {reason}`. A relevance judge that fails lets the reply through (logged `relevance unchecked`).
- **A reply may never promise what no tool did** (`NARRATES_ACTION_RE` + `changedState` in `reply-check.ts`). A reply claiming a state change ("added it to day 3", "i'll get that on the board", "locked in", "saved") is **discarded** unless a state-changing tool ran that turn (`STATE_CHANGING_TOOLS`: add_suggestion, avoid_category, record_split/regroup, update_my_setting, update_trip_setting, request_tasks, redo_today, propose_freeform_claim, request_photo_bonus). Reason logged as `narrated_uncompleted_action`. This is the "got it bob, profile locked in" bug class caught at the vetter, so it covers every future instance. Offers and questions ("want me to add it?", "should i put it on day 3") are not claims and pass. **"sort" is deliberately not a verb in the pattern**: "i'll sort that once we're done" is real survey copy and a deferral, not a claim.
- **A pasted link is read BEFORE the conversation turn** (`resolveFirstLinkForContext`, `lib/handlers/social-links.ts`), and the venue it names goes into the prompt. Without it the model gets a bare URL, has no venue to pass to `add_suggestion`, and reaches for `search_web` on the Instagram shortcode, which can never return anything. Verified on the live model: the same message goes from `search_web("instagram reel DRjSL_pEW3X Tokyo")` to `add_suggestion({"place":"Shibuya Sky"})`. Reading only, ~1.4s, no place row and no message; the queued row stays for the cron and whichever path writes first owns it. Only the FIRST link is read inline; the rest stay on the queue.
- **`search_web` refuses a URL** (`looksLikeUrl`, `lib/handlers/web-search.ts`): a URL, a platform name, or a bare shortcode comes back `{ok:false, reason:"is_a_url"}` without burning a call. Searching the web for an Instagram shortcode can never return anything useful, and the resolved link context is already in the prompt.
- **Photo bonus ceiling:** at most 5 and at most 40% of base points (`photoBonusCeiling`, `lib/game/scoring.ts`). Clamped when every task row is built (logged `[japlan.generate] photo_bonus_max clamped` with the model's original) and again at claim time (`photoBonusMaxFor`), so old rows are bounded too.
- **A setup answer is only written when the person actually gave it.** Same bug class as the trip-settings corruption: the flow asked "where we headed?", nobody named a city, and the next message said "got it: kronjo, indonesia". A resolver handed text that is not a destination will find the nearest-sounding city in it rather than refusing, and `inferPlaceTimezone`'s prompt presupposes the text IS a destination.
  - `looksLikeDestinationAnswer` (`lib/game/setup.ts`) gates the resolver: a question, a correction, a sentence over six words, or anything matching "did you / where did / get that / come from" is `confidence: "unusable"` and **re-asks** instead of confirming.
  - `ResolvedDestination.confidence` is `lookup` (offline table), `places` (real lookup), `raw` (their own words verbatim, which is honest) or `unusable` (never written). **A model display name is only ever used when a places lookup corroborated it**, because a model asked "where is this" always names somewhere.
  - Every setup answer logs `[japlan.setup] step destination.resolved` with the raw string, what came back, the confidence and whether it came from the model.
- **A question or a correction during setup is not an answer to it.** The flow used to consume whatever arrived, so "japlan where did you get that city from" became the DATE answer and got "couldn't read those dates" - and a wrong value could never be corrected, because the correction became the next answer. `setupMessageIntent` classifies answer / question / correction; a non-answer is replied to and the pending question **re-asked**, writing nothing. `asideField` answers the field they asked about rather than the one that happens to be pending. A correction replies "my bad, let's redo that one" and re-asks, which is what makes correcting possible at all. `isSetupSkip` still counts as a real answer. `setup-answers.test.ts` pins all of it.
- **The setup/survey DM handoff** (`lib/handlers/survey.ts`). The gate that says "the organizer is setting the shared city..." sits near the top of the DM path and used to have no exemptions, which produced three live bugs from one cause: it fired above the survey continuation, so the first answer after the survey started was swallowed, the survey never advanced, and every later DM got the identical line forever. The organizer's name still showed as a phone number precisely BECAUSE their name answer never landed. Three exemptions now, and none of them are optional:
  - a survey **already in progress** is never blocked, whatever `setup_state` says;
  - the **organizer** is never blocked, because their setup happens in the group chat and they cannot be waiting on themselves;
  - it is said **once per person** (`participants.setup_pending_told_at`, migration `2026-10-07`), then silence.
- **A phone number is never printed as a name.** Linq supplies one when it has no display name, and a participant keeps it until they answer the name question. `personLabel` (`copy.ts`) renders anything phone-shaped as "the organizer".
- **The survey's opening message is ONE message.** `startSurvey` joins `SURVEY_INTRO` and the first question with a **blank line**, not a space: space-joining them produced "...if i need a safety detail right. a few quick ones so the tasks fit you...", which reads as two messages glued together. `SURVEY_V2` has its own `first_name` prompt (`"what should i call you?"`); the legacy one re-explains "skip" that the intro already covered and re-opens after the intro has opened, so reusing it explained skip **three times** in one message. `setup-handoff.test.ts` pins all of this.

Finishing the survey replies once: the close, that person's board (`boardForNewlyReady`, today or day 1 marked provisional), then the sidequest question. Nobody else is sent anything. Anyone already finished when setup completes gets board + sidequest question in one DM (the organizer's rides in the setup reply). The cron serves `surveying` trips: activates one with a finished survey; if nobody has finished, posts `waitingOnSurveysLine` once (`trips.waiting_notice_sent_at`); at board time each unfinished person gets their next question by DM, once a local day (`participants.survey_nudged_on`, `lib/handlers/survey-nudges.ts`). Board requests log `path`: `served_existing`, `regenerated`, `refused`.
- **Stalled events:** `sweepStalledEvents` (after each webhook, at most once a minute per instance, and on the cron) re-dispatches unprocessed inbound messages 2-30 minutes old, once, and logs older ones `[japlan.webhook] dropped`. A dispatch that throws is marked processed (the person already got "that's on me").
- **Trip stats** (`participant_stats`, `lib/handlers/stats.ts`, definitions in `lib/game/stats.ts`): per person, bumped atomically as things happen (`bump_participant_stats`). `itinerary_items_total` moves with task writes and deletes (a redo or regeneration subtracts what it removes); freeform and unowned shared tasks do not count. Awards bump tasks_completed (capped included), photos, bonuses, freeform, distinct days and places; late photo bonuses bump photos/bonuses. `distance_km` stays 0 until claims store location; `sidequests_claimed` until sidequest delivery exists. `statsDrift(tripId)` compares the counters with a full recount (`recomputeStats`); tested after a simulated trip. Group totals are summed on read. Wrapped's contract is `WrappedData` (`lib/game/wrapped.ts`, per-field sources in `WRAPPED_SOURCES`); `wrappedDataFor` builds it from a real trip. The page still renders the fictional fixture.
- Addressed fallthrough (no code, no claim match) goes to the conversation tool loop (`lib/handlers/conversation.ts`), not silence. Help (`japlan help`, `japlan ?`, etc.) is an addressing intent and never a freeform claim.
- `lib/game` must stay network-free. Handlers own I/O.

## How to run and test

Env: `.env.example` / Vercel project env. Solo flag: `JAPLAN_SOLO_MODE=true` (also `1` / `yes`). Group behaviour must not change when the flag is false.

Solo trips skip group-only survey questions (`GROUP_ONLY_QUESTIONS`: splitting and its follow-up) and the stake setup question, get no morning standings post, and fold "we're live" into the reply they are already getting (their DM is the trip chat).

Solo DM loop (does not exist unless the flag is on):

1. DM `japlan solo` -> creates `trips.is_solo` row, asks the organizer setup (you are the organizer), then the survey.
2. `japlan skipsurvey` -> default survey answers. A trip only activates once setup has a destination and dates, so answer those or run step 3.
3. `npx tsx scripts/seed-profile.ts` -> Tokyo profile, dates (today JST + 4 days), `setup_state=done`, activates if surveys are done. Set `TRIP_ID` if more than one solo trip.
4. Trigger the board:
   `curl -H "Authorization: Bearer $CRON_SECRET" "https://<host>/api/cron/daily-board?force=1&trip_id=<uuid>"`
5. Claim by sending a code (`A1`). Photo is optional bonus.
6. Wipe board, keep profile: `TRIP_ID=<uuid> npx tsx scripts/reset-trip.ts`. Delete the trip and everything under it: add `--hard` (needs the cascade migration).

Trip lifecycle (organizer only, keyword required): `japlan board time 7am` (sets `trips.board_time`), `japlan setup` (re-run setup mid-trip), `japlan end trip` then `japlan end trip confirm` (state `complete`, final standings + stake), `japlan new trip` (only when no open trip; bootstraps the same chat again). One open trip per chat: `getTripByChatId` returns the newest non-complete trip.

**Before deploying a change to the trip query, run `npm run verify:embed`.** Trip lookups use a PostgREST **embed** to pull legs in one call, and `lib/test/fake-supabase.ts` does not implement embed syntax, so nothing in `npm test` exercises the real join. `check:schema` will not catch it either: every column exists, it is the *relationship* that might not resolve. `scripts/verify-embed.ts` is read-only and checks three things against the live database, exiting 1 on any failure: a real trip comes back with legs embedded and populated, a trip with no legs rows synthesises a single one, and a deliberately broken relation name falls back to plain `TRIP_COLS` rather than throwing. It caught a real bug on first run: `cityFor` was leaking the synthesised leg's display placeholder ("the trip") into geocode, holiday and ticket queries.

**Before deploying, run `npm run check:schema`.** Three outages have been the same bug: a query started selecting a column, its migration was never run, every trip lookup threw `42703`, and the webhook still returned 200, so the bot went silently dead. Three guards now:
- `npm test` (`lib/db/schema-contract.test.ts`): fails if the code selects a column no migration creates, or one `SCHEMA_CONTRACT` (`lib/db/schema-contract.ts`) does not list. This is the one that catches it before a deploy exists.
- `npm run check:schema` (`scripts/check-schema.ts`): read-only; prints each migration as applied or NOT APPLIED against the live database, names the migration for any column the code selects and the database lacks, and exits 1.
- Runtime (`lib/db/schema-check.ts` `verifySchemaOnce`): one probe per cold start from the webhook's `after()` and the cron, logging `[japlan.schema] MISSING COLUMN trips.play_mode` at error level. Never blocks a request, never throws.
Adding a column to a query means: write the migration, add the column to `SCHEMA_CONTRACT`, run the migration, then deploy.

Migrations live in `lib/db/migrations/`, run in filename order in the Supabase SQL editor. `2026-09-26-survey-v2-engagement.sql` (prefs_json, profile_md, group_profile_md, engagement_json, `chat_messages`) must run before deploying this code: `TRIP_COLS` selects the new trip columns, so every trip query fails without it. Then, in order: `2026-09-27-clamp-photo-bonus.sql` (data fix only; claim time also clamps), `2026-09-28-gating-retries-sidequests.sql` (nudges, waiting notice, event retries, sidequest tables), `2026-09-29-participant-stats.sql` (`participant_stats` + `bump_participant_stats`). Then `2026-09-30-group-onboarding-and-play-modes.sql`, `2026-10-01-group-decisions.sql`, `2026-10-03-trip-legs.sql` (`trip_legs`, `places.leg_id`, `multiplier_days.leg_id`, and a backfill making every existing trip one leg; not in `TRIP_COLS`, so a missed run degrades to a synthesised single leg), `2026-10-04-social-links.sql` (`social_links`, `places.source_url` / `address` / `resolved_at`), `2026-10-05-show-suggestion.sql` (`trips.show_suggested_at`, not in `TRIP_COLS`), `2026-10-06-trip-events.sql` (`trip_events`), `2026-10-07-setup-pending-notice.sql` (`participants.setup_pending_told_at`), and `2026-10-02-day-multipliers.sql` (`multiplier_days`, `trips.multipliers_checked_at`, and `tasks.day_multiplier` / `multiplier_reason`). None of 27-29 or 10-02 touch `TRIP_COLS`: without them the new features log and do nothing, and stats bumps log `[japlan.stats] bump failed`. `multipliers_checked_at` is deliberately kept out of `TRIP_COLS` so a missed migration stops the holiday lookup (logged `[japlan.multipliers] step ... migration 2026-10-02 applied?`) instead of breaking every trip query. Both `tasks` columns ARE in `TASK_COLS` (`lib/handlers/claims.ts`) and in `SCHEMA_CONTRACT`, so 10-02 must be run before deploying this code or every claim lookup throws `42703`. `lib/db/checks/one-open-trip-per-chat.sql` verifies the partial index and cascades inside a rolled-back transaction. Claim races depend on the `claims_one_winner_per_task` index (migration 2026-09-19): check it exists with `select indexname from pg_indexes where tablename = 'claims'`.

**Settings are editable any time, and the model does not enforce rules.** The conversation system prompt says so explicitly (`CONVERSATION_SYSTEM_PROMPT`: "you do not enforce rules"), and the model has tools for everything people ask to change: `update_my_setting` (any own answer, plain words via `lib/game/settings.ts`; private ones confirmed in DM), `update_trip_setting` (organizer: destination, dates, difficulty, board time, stake), `request_tasks` ("7 attractions": that many or what fits in the usable time, with the reason; pace is a default, `tasks_per_day` a standing request), `redo_today`. Commands: `japlan settings` (own values, in DM), `japlan resurvey` (first question again, skip keeps old answers, boards keep coming). Do not add "can't"/"limit"/"only"/"locked" language to the prompt, tool descriptions or help text: the model quotes it back as a rule.

No longer asked (nothing reads them now that teams form from conversation): `competitiveness`, `social_travelled`. `interests` and `nightlife` became `interest_picks`; old answers still count. Ratings are read but never written (PLAN's post-anchor rating prompt is not built).

`japlan resurvey` restarts the survey in DM; `japlan settings` lists and explains how to change answers.

Hand-written day-1 board: `npx tsx scripts/seed-tasks.ts`.

Local: `npm test` (vitest). End-to-end handler tests run against `lib/test/fake-supabase.ts`, which enforces the schema's unique constraints. Capture inspector: `npx tsx scripts/inspect-captures.ts`. Claim-query probe: `npx tsx scripts/probe-claim-queries.ts`.

Logs: `vercel logs --follow` drops lines under concurrency. **Vercel dashboard logs are the source of truth.** Prefixes: `[japlan.webhook]`, `[japlan.dispatch]`, `[japlan.claim]`, `[japlan.solo]`, `[japlan.conversation]`.
